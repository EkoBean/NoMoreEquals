# Wishlist

長期想做、但還沒排進實作的方向。每個項目記錄「想解決什麼、為什麼現有架構不夠、可行性、已知阻礙」。

這裡不是實作計畫 —— 沒有步驟、沒有檔案清單、沒有工期。確定要動手的項目會另外寫成 `docs/superpowers/specs/` 底下的 spec。

## 現況基準：轉換到底發生在哪一層

先把這件事寫清楚，因為它很容易被記錯成「Enter 之後才攔截替換」。**不是。** 目前的主路徑就已經在 IME 訊息層。

1. **視窗 subclass。** `ImeCompositionTracker` 對 `FFXIVGAME` 視窗掛上 `SetWindowSubclass`，攔 `WM_IME_COMPOSITION`。
2. **上字瞬間改寫（主路徑）。** 收到 `GCS_RESULTSTR` 時讀出 IME 的上字結果、跑轉換，然後**把 `GCS_RESULTSTR` 這個 flag 從 lParam 拔掉** —— 遊戲從頭到尾沒收到過中文。轉換後的字改由 `InsertText` 補進聊天欄。
3. **Enter 時的 `SetText`（僅安全網）。** `ConvertBeforeSend` 在 `WM_KEYDOWN` Return 時整行重寫。這條路只處理主路徑處理不了的情況 —— 主要是跨兩次 IME 上字的自訂片語規則，那種規則只能對整行套用。它不是主要機制。

所以本文件底下談的「介入 IME」，指的是**比 `GCS_RESULTSTR` 更早、更深**的層級，不是「從 Enter 改成 IME」。

## 項目：介入 IME 組字過程

### 想解決什麼

目前在上字瞬間介入，已經比事後修字乾淨很多，但仍留下一批結構性的麻煩。這些麻煩在原始碼註解裡都寫明了，都是同一個根因：**遊戲的 `AtkComponentTextInput` 才是文字狀態的擁有者，外掛只能從旁邊插手。**

- **`=` noise。** 遊戲的 `RawString` 會把 AXIS 畫不出來的字填成 `=`，所以組字中的緩衝區內容不可信。`ChatBufferHeuristics.IsMostlyEqualsNoise` 整個存在的理由就是繞開這件事。
- **時序。** `SettleTicks` 要等 IME 自己的收尾訊息跑完才能 `InsertText`，等太久會被其他按鍵插隊、等太短會被 IME 蓋掉。這個常數沒有理論值，只有取捨。
- **caret 單位不明。** `CaretIsAtEndOf` 得同時接受 rune 數和 UTF-8 byte 數兩種讀法，因為遊戲的 `CursorPos` 到底在數什麼沒有文件，而它量的又是被 `=` 汙染過的 `RawString`。
- **TSF 漏接。** 走 TSF 而非 IMM 的輸入法，`GCS_RESULTSTR` 那條攔截可能整個沒觸發，只能靠 Enter 的安全網補。

### 已評估的三個方向

| 方向 | 介入層級 | 可行性 |
|---|---|---|
| **A** 改寫候選清單內容 | IME 進程內部 | **不可行** |
| **B** 改寫 COMPSTR | 組字中的注音串 | **無價值** |
| **C2** 自建輸入層 + 每幀同步 | 外掛 | **可行但重（選定方向）** |

#### A：改寫候選清單內容 —— 不可行

構想是讓使用者打「ㄌㄩˋ」時，候選視窗直接顯示「緑」而不是「綠」，選字當下看到的就是最終結果。

做不到。那個候選視窗是**輸入法自己的進程**畫出來的 UI（微軟注音是獨立的 TSF text service），候選字來自輸入法自己的詞庫。外掛跑在遊戲進程裡，沒有任何受支援的手段去改寫另一個進程的候選來源。

真要做，等於自己寫一套輸入法（TSF text service），並且要求使用者去 Windows 設定裡把輸入法切換成它。那已經不是 Dalamud 外掛的範疇，是另一個產品，而且會接管使用者在**所有**程式裡的中文輸入。不做。

#### B：改寫 COMPSTR —— 無價值

構想是改寫組字中那段有底線的字串。

對繁中注音沒有意義：COMPSTR 在選字前是**注音符號**（ㄌㄩˋ），不是漢字，根本沒有缺字問題。等它變成漢字的時候，那已經是 `GCS_RESULTSTR`，也就是現在已經在攔的地方。沒有可做的事。

#### C2：自建輸入層 + 每幀同步 —— 選定方向

**形狀。** 外掛自己維護一份 shadow buffer 作為文字狀態的**唯一真相**。IME 的組字與候選照常由系統處理，上字結果進外掛的 buffer 而非遊戲的。每一幀把轉換後的字串 `SetText` 回遊戲文字框，讓遊戲原生的聊天欄一直顯示正確內容。送出時遊戲讀到的自然就是轉換過的行。

**為什麼值得。** 上面那四個麻煩會一次消失，因為它們全都是「外掛不擁有文字狀態」的症狀：緩衝區內容由外掛自己維護就不會有 `=` noise；插入時機由外掛決定就不需要 `SettleTicks`；caret 位置由外掛自己算就沒有單位歧義；TSF 與 IMM 都只是餵進同一個 buffer 的兩個來源。

**首要風險：caret 權威。** 這一點沒解決，C2 就不成立。

現有程式碼已經實測過：`CursorPos` 是遊戲輸入處理的**輸出**，不是輸入。同時寫入 `CursorPos` / `SelectionStart` / `SelectionEnd` 三個欄位，值會留在那裡（當下讀回來一致，下一幀讀回來也一致），但畫面上的 caret 節點不會動 —— 遊戲只在處理真實輸入時才重新定位它。所以現在推進 caret 靠的是合成 `End` / `Right` 按鍵，不是直接寫值。

C2 要求的是**每幀**的 caret 權威。靠合成按鍵每幀去追一個外掛自己算出來的位置，不是個能成立的方案。

**前置探索。** 動手之前要先回答一個問題：有沒有辦法真正取得 caret 的寫入權（hook 遊戲的輸入處理、找到真正的定位入口、或其他手段）？**答案是否定的話 C2 就不做**，回頭考慮 C1（外掛 buffer 為真相、但 overlay 當成玩家實際在看的輸入框，遊戲文字框在打字中不保證正確、只在送出時寫回一次）。C1 的代價是遊戲原生聊天欄在打字過程看起來是壞的，好處是完全不需要碰 caret。

在那之前，其餘設計細節不值得先想。
